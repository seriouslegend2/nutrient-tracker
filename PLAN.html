Product Boundary

IMPLEMENTED A multi-user nutrition tracker with onboarding, manual and assisted meal logging, safety-aware goals, hydration, reports, a conversational assistant, and an admin dashboard.

DEFERRED The repository is not a complete food-data platform, medical system, media archive, offline PWA, or advanced BI product. Deferred work below is deliberately excluded from the current contract.

Implemented Architecture

browser
  -> Next.js 16 BFF (customer :3000 or admin :3001)
       -> Supabase SSR auth only
       -> signs user-specific HS256 backend bearer
  -> FastAPI /api/v1
       -> validates bearer and loads roles from user_roles
       -> server-side Supabase service-role client
  -> Postgres 17

The browser uses same-origin application routes for product data. The public Supabase URL and anon key configure email/password authentication and session handling, while the service-role credential exists only in FastAPI and the offline seed script. FastAPI's service-role calls bypass RLS, so repository user scoping and backend RBAC are the primary authorization boundary. RLS is enabled as defense in depth for non-service-role database paths.

Customer signup/login uses Google OAuth through a server route with prompt=select_account. Google lists accounts already signed into the browser; Supabase creates a first-time identity or signs in the existing identity, and the customer callback exchanges the OAuth code server-side. The dashboard remains a separate sign-in-only operator surface. The session bridge applies HTTP-only, same-site, and production-secure cookie options, and both apps implement logout. BFF-to-FastAPI bearers contain user_id, have no expiry claim, and are signed with matching server-only secrets in the backend and both BFFs.

A supplied service-role key was exposed and must be rotated before use. Its value must never appear in documentation or frontend configuration. Actual local environment files contain public project values and placeholders for the rotated service-role and replacement JWT secrets; checked-in examples stay generic.

Implemented AI Surface

The only implemented agent names are nutrition_chat and media_extraction.

  • nutrition_chat has read tools for dish search, meal history, and goal status plus explicitly gated mutation tools for meals, goals, water, weight, and portions.
  • media_extraction normalizes JPEG/PNG/WebP food photos, explicitly label-hinted images, supported audio, and food-diary PDFs before chat.
  • Ordinary image uploads use three extraction samples. Review cards expose editable mass and ranges before commit.
  • PDF rows become reviewable meal items. The selected confirmation date and meal type apply to the batch.
  • Upload bytes are transient and not persisted. Message text, structured output, metadata, and agent-run telemetry are persisted.
  • Without an OpenAI key, AI calls report disabled while the manual product remains usable.

Implemented Dashboard

The dashboard is sign-in-only for separately provisioned operator accounts. The admin UI verifies the signed-in user at the BFF, checks the backend-provided admin role in the UI, and relies on FastAPI permission checks for enforcement. Dashboard access is granted by inserting the admin role in user_roles. Logout clears the local Supabase session. The dashboard provides server-paginated users and per-user overview, meals, goals, preferences, conversations, and agent-run panels. Aggregate cards cover users, recent meals, agent success/latency when runs exist, and portion-resolution mix.

User search, filtering, sorting, account mutation, body-history, progress, audit, and food-database administration are not implemented.

Data And Migrations

Fifteen ordered migrations define identity/profile tables, global and user category portions, meals, concurrent cadence-aware goals, explicit activity logs, preferences, water logs, communications, agent runs, audits, formulas, atomic versioning RPCs, triggers, grants, and RLS. An auth trigger creates app_users and the customer role from auth.users.

The migration seed supplies all 18 category defaults. The optional Python seed contains 61 curated as-entered dish rows and no demo account. It is a starter corpus, not a full national or commercial food database.

Intentionally Deferred Backlog

  • Video extraction. Video MIME types are rejected with a user-readable response.
  • Raw media storage, later replay, and administrator visual inspection.
  • Page-count and audio-duration enforcement beyond current byte limits.
  • Automatic nutrition-label image classification beyond explicit text/filename hints.
  • Ranked alias search, BM25, embeddings, and combined lexical/vector retrieval. Current search is normalized substring matching.
  • A large food/demo seed and a Food DB administration interface.
  • Advanced projections, arbitrary report-range controls, full operational analytics, and additional admin panels.
  • Account export, self-service account deletion, offline/service-worker behavior, and a general profile/preferences editor.
  • Generated OpenAPI client types. Frontends currently maintain local interfaces.

Acceptance And Verification Plan

  1. Keep Ruff, configured mypy, import-linter, backend tests, frontend typechecks, and frontend isolation green in CI.
  2. Require pgvector/Postgres in CI, apply all migrations from empty, and fail if integration tests skip.
  3. Before deployment, rotate the exposed service-role key, create a new shared JWT secret, link a disposable hosted Supabase project, and verify migration push, PostgREST, auth bootstrap, and real policy behavior.
  4. Configure a Google Web OAuth client, enable the Supabase Google provider, allow the Supabase Auth callback in Google, and allow the customer /auth/callback in Supabase URL Configuration. Drive first-time Google signup, returning-user login, account selection, onboarding, logout, dashboard sign-in, role denial, and admin-role access.
  5. With an OpenAI credential, exercise live chat, photo, label-hinted photo, audio, and PDF paths, including failed and confirmed drafts.

Steps 3-5 remain external runtime verification, not completed product evidence. Local evidence is 15 migrations, 98 backend tests, 31 customer tests, 22 dashboard tests, Next.js 16.3.1 in both lockfiles, and zero production vulnerabilities from both frontend audits. The hosted non-agent suite passes all 15 scenarios.
