  • Nutrition formulas, calorie floors, safe-rate clamps, target-BMI and medical guards, and behaviour goals pass worked assertions.
  • Portion resolution order, unknown fallback, body/profile refresh, coherent meal-day versions, atomic preference/portion swaps, concurrent goals with one primary, cadence progress, activity logs, and schema presence are tested.
  • RLS enablement is checked on user-owned tables.
  • Privileged security-definer functions are checked as unavailable to public, anonymous, and authenticated roles and available to the service role.

The standalone database suite is not hosted Supabase. The separate hosted Playwright run exercised PostgREST, Supabase sessions, and BFF-issued user JWTs. It did not exercise own-row policy access through a direct authenticated database client; backend database calls use service role and bypass RLS by design.

Current Limitations

  • Search is normalized substring matching, not ranked or semantic retrieval.
  • The optional dish seed contains 61 curated rows; the database migration contains 18 category defaults. There is no demo account seed.
  • Raw upload bytes are not persisted, so media replay and later visual admin inspection are unavailable.
  • Image/audio/PDF byte limits exist; PDF page and audio-duration limits do not.
  • Nutrition-label routing requires an explicit text or filename hint.
  • The customer manifest has no service worker/offline implementation. Export, self-service deletion, and a general post-onboarding profile editor are absent.
  • The dashboard intentionally omits user search/filter/sort, Food DB administration, body history, goal progress, and audit panels.
  • Frontend API interfaces are handwritten. There is no generated shared type/client artifact.
  • Focused Vitest suites cover Google OAuth routing, safe redirects, backend JWT generation, API clients, pagination, and dashboard panel contracts. The existing hosted Playwright evidence predates the Google-only customer login change.
